# Hints 能否转成 RL 奖励（建模讨论稿）

2026-10-31（America/New_York）。用户提出的问题：协议里的 13 类任务提示（HINTS）能否转化为 RL 奖励问题？用户认为这种控制是需要的。

**本页性质**：§1–§2 是事实，§3–§5 是讨论稿（CC 的读法），§6 是待决问题。研究决定由用户做。hint 原文和选取规则见 [protocol/CAPTION_V51.md](../protocol/CAPTION_V51.md) §3。

## 1. 事实：hint 现在的位置

- **教师生成轨迹时**，prompt 里按题最多加 2 条 hint；**导出给学生的 SFT 视图去掉了 hint**，SYSTEM 不变（据 `caption_v51.py` 的模块说明）。
- **RL 题池 4,096 题和 E1 552 题**的首轮 prompt 里都没有 hint（逐题检查）。
- 所以 hint 只通过教师的 SFT 轨迹间接影响了学生；RL 阶段没有任何与 hint 对应的信号。现在的奖励只有终答 0/1，加上硬检查清零（见 CAPTION_V51 §5、§7）。

## 3. 讨论：把 hint 变成训练信号的三种方式

一条 hint 是“在某一类题上，好的行为长什么样”的文字描述。要变成训练信号，可以放在三个不同的位置：

| 方式 | 改动位置 | 做法 | 改变的是 | 依赖 |
|---|---|---|---|---|
| H1. 条件输入（控制） | prompt / 数据 | RL 时也给 hint，再逐步撤掉（scaffold dropout） | 给策略一个条件；不改奖励 | 无标注；评测时没有 hint，所以要撤 |
| H2. 可验证谓词 → 奖励或约束 | 奖励 / 硬检查 | 把 hint 改写成能对轨迹打勾的条件，满足给分，或违反清零 | 偏好（加奖励项）或可行域（硬检查） | 有的只需规则，有的需要真值，有的需要评审 |
| H3. hint → 标注方案 → 导师的过程信号 | 过程奖励 | hint 决定这类题要标什么（单框、多框、有序框链、点、路径），再用导师的“目标逼近 / 探索 + gate”打分 | 偏好（过程项） | 真值标注 |

主线框架的约束：任务奖励必须保留且为主；过程奖励另加；不为每种现象单独配一个奖励；reward hacking 无法被平衡掉，只能尝试 shaping。

## 4. 讨论：13 类 hint 逐条拆解

“检查类型”一列：R = 只用轨迹文本和动作的规则就能判；G = 需要真值（框、多框、点或路径）；J = 需要评审（看图或语义判断）。

| key | hint 要求的行为 | 在我们轨迹里可观测的量 | 检查类型 | 可能的信号（位置） | 对应论文 / 导师 | 风险 |
|---|---|---|---|---|---|---|
| count | 先说计数单位和整个区域；必要时切成不重叠的部分；每部分写小计并引用视图；在 CALC 里加总；查边界 | 裁图是否把目标区域切成不重叠的块；CALC 行；小计是否引用视图 | R（CALC 存在、加法自洽）+ G（各块并起来是否覆盖目标区域） | 探索覆盖目标区域（过程）；选项是数字时，按与真值的相对误差给部分分（任务奖励） | 论文计数：先一次框出全部，再汇总；R = 0.7·exp(−3·\|ŷ−y\|/(\|y\|+1)) | 部分分会改变偏好；CALC 自动校验曾经出错（百分号问题） |
| table | 按行表头找行、按列表头找列，并把两者和数值一起写出；注意单位、脚注、合计行；绑定改了就撤回依赖的结论 | 裁图是否同时覆盖单元格、行表头、列表头；caption 是否写出两个表头 | G（单元格框 + 两个表头框，多框）+ R（两个表头是否都被提到） | 多框逼近：三个框都要被覆盖（过程） | 用户：多框是“探索 × 单框”的交叉 | 一张大裁图同时盖住三处也能拿分（整图裁剪问题） |
| chart | 读值前先认清坐标轴、图例和标记的对应、分面；对照最近的刻度线；排序前先数全；规则写 RULE，算术写 CALC；同色不等于同一系列 | 图例、数据点、坐标轴三处是否都被看过；先后顺序 | G（多框，可能有序）+ R（RULE / CALC 行） | 有序多框：图例 → 数据点（过程） | 论文空间推理：意图 → 定位 → 关系推理 | 顺序要求可能过度约束 |
| map | 先读图例、比例尺、方向；通过图例绑定符号；**一段一段追踪路线**（穿过一个区域不等于连通，交叉不等于路口）；局部裁图没看到连接，不能证明不连通 | 裁图序列是否沿着路线前进 | G（路径：有序框链或点链） | 路径逼近：途经区域的双向覆盖（过程） | 论文迷宫 / 线路追踪；O3Bench 有有序的版面框链 | RL 题池目前 0 题命中；需要路径标注 |
| instance | 先找到满足全部条件的那个实例，再读它的属性；有部分匹配的候选时，核对能区分它们的条件；后续视图里保持同一个实例；换候选时说明哪些旧属性作废 | 最终引用的视图是否包含目标实例、是否混入干扰实例 | G（目标框 + 干扰框） | commit 引用的视图覆盖目标、不以干扰框为主（过程） | 论文 Reference Gap；细粒度计数记录“被排除的负候选” | 需要标干扰实例 |
| text | 只写看得见的字符，看不清的写 ?；不按词义、品牌、地名补全 | 转录与 OCR 的一致性 | G（OCR 文本 + 框）或 J | 转录与 OCR 一致（过程）；OCR 本身也可以作为工具（导师） | 导师：OCR 也算工具 | OCR 本身会出错 |
| relation | 两个对象都要定位；在同一视图里判断关系，或者用各视图在原图中的位置判断；题目给了别的视角时要说明换算 | 两个对象是否都被裁图覆盖 | G（两个框）——有了两个框，关系本身可以直接从坐标算出来 | 两框都被覆盖（过程）；关系对错由任务奖励管 | T08（“F 上方”）：字读对了，空间关系错了 | 命中 1,323 题，规则较宽（含 left/right 等常见词） |
| color | 区域暗、模糊或偏色时先说明，再和附近的中性参照比较；不按品牌或常识推颜色 | 是否看过参照区域 | J（颜色判断） | 弱；主要靠任务奖励 | — | — |
| search | 大图里某区域没有目标时要说出来，回到之前的视图去别处找；简要列出已经排除的区域 | 已排除区域列表（记忆）；是否重复进入已排除的区域 | R（新裁图和此前“未找到”的裁图重叠多少）+ G（排除是否属实） | 导师的探索程度；重复进入已排除区域不再加分（过程） | 论文迷宫：DFS 回溯、探索完整度；用户提出的记忆问题 | 探索项和成本目标方向相反（gate） |
| aerial | 依靠形状、阴影、上下文识别；计数时沿道路、行列、街区等可见结构分块 | 同 count | 同 count | 同 count | 同 count | RL 题池 0 题 |
| screen | 照原样读标签；按标签和位置识别元素；不假设标准界面布局 | 是否定位到正确的界面层 / 元素 | G（元素框） | 同 instance | T07：被前景内容拉走 | RL 题池按此规则 0 题（缺 material 字段） |
| compute | 先给出读到的数值及其视图；需要的约定或公式写一行 RULE；计算写 CALC；输入被纠正时重新计算 | CALC 结果与最终选项是否一致 | R（CALC 结果对应的选项 = 最终字母） | 一致性检查（硬检查或奖励项） | 论文 Quality RM 的“思考与答案一致”；T03 / T04 / T07 的不一致 | 只能检查自洽，不能保证读数正确 |
| puzzle | 先描述实际看到的元素和规律（位置、数量、形状、朝向），再套规则；规则写 RULE | RULE 行是否出现、出现在描述之后 | R（弱） | 弱 | — | RL 题池 0 题 |

## 5. 讨论：从这张表能看到的结构（CC 的读法）

1. **需要真值的 hint 占多数**：table、chart、map、instance、relation、screen 都要多框或路径，而 RL 题池目前一个框也没有。所以 H3 的第一步是确定“每类 hint 要标什么”，也就是标注方案，再谈奖励。
2. **只靠规则就能做的有三类**：
   - compute：CALC 结果和选项一致；
   - search：不重复进入已排除的区域；
   - count：CALC 加法自洽。
   它们不需要标注，但只能保证自洽，不能保证读数正确。
3. **H1（RL 时给 hint 再撤掉）不改奖励**，本质是课程学习或条件控制；和“教师用 hint、学生不用”的现有做法一脉相承。
4. **导师的“目标逼近 / 探索 + gate”是 H3 的通用打分器**：单框题用逼近；多框题要先定聚合方式；没有目标的题（725 题带“不存在”选项，其中 14 题答案就是它）只用探索。
5. **论文对应**：计数部分分对应 count；路径和迷宫对应 map 与 search；Reference Gap 对应 instance、relation、screen；Quality RM 的一致性对应 compute。
